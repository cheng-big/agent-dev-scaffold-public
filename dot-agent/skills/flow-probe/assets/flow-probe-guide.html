flow-probe —— 浏览器真流程测试方法

对着业务流程规格，把每条流程当真实用户跨端走一遍：浏览器点真页面 + 后端回查坐实 → 出问题清单 → 闭环修复。不是接口 200 冒烟，不做假绿。

① 这套方法在做什么

一个业务平台功能"开发完了"，不等于每条业务流程"真跑得通"。这套方法照流程规格(时序图/流程文档)逐条流程、跨端(公众门户/管理后台/移动端)、用浏览器点真实页面驱动，每一步都用后端权威回查坐实，评估"按应然是否真跑得通"，产出一份单文件交互 HTML 报告(正常流程逐步骤 + 当前问题 + 修复意见)，再闭环修复。

它比接口测试强在哪：接口测试只验"POST /review 返回 200"；这套方法验"审核员打开审核待办页，真的能点到通过按钮把它办结吗"——后者才是真实用户的路径，很多缺陷(页面缺按钮、列表看不到该数据、下拉设不进值)只有点真页面才暴露。

② 一图流水线

流程规格(时序图/泳道/状态机) ──抽泳道──▶ 步骤→端映射 (应然真源) │ 角色/权限 + 字段级需求 ─────────────────────┤ ▼ 摸实现(后端 controller/状态枚举/种子 · 前端 路由/按钮/公众端点) ▼ 写探针(逐步骤 · 落端 · 浏览器点真按钮 · 后端回查坐实) ▼ 起隔离栈跑(建库→迁移→后端→前端→Playwright→拆栈) ▼ 判定 PASS / MISMATCH / GAP / ERROR / INFO (每步带 端 · 驱动UI-HTTP · 修复意见 · 截图) ▼ systems/*.json ─▶ ★ report.html (单文件交互报告 = 最终交付物) + 问题清单 ▼ 闭环：问题 → 改产品代码 → 重跑该系统 → 转绿

③ 8 步流水线

  1. 抽泳道：从时序图 participant 逐步骤抽「角色(谁) + 端(公众门户/管理后台/移动端…) + 是否跨系统」。别把跨端流程全塞管理后台。
  2. 摸实现：后端 controller/状态枚举/种子账号；前端路由、页面、真实按钮(看表格 prop= 定位可见列、@click= 定位动作按钮)。
  3. 定账号：每个「端×角色」一个浏览器上下文；注意分级路由(审批区划常取提交人区划，提交人须辖区账号否则待办为空)。
  4. 写探针：每步 step(端, 应然, 实测, 判定, 驱动, 修复意见, 截图)；有页面就浏览器点真按钮(uiDrive/审核待办点通过)，后端回查坐实，点不到就判红不兜底。
  5. 起隔离栈跑：建隔离库→迁移→后端→前端→Playwright→拆栈。headless 先验，再有头出图。
  6. 判定：见下表；每步双维度 端 + 驱动(UI/HTTP)。
  7. 报告：探针落 systems/<code>.json → 合成 report.html(最终交付物)。
  8. 闭环修复：问题→定位(前端/后端/迁移/契约)→改产品代码→重跑→转绿。
判定含义严重度
PASS实测与应然一致，且后端回查坐实—
MISMATCH能跑通但口径分叉，或断言不成立P2
GAP应然有该步/态，实现无落地P1
ERROR报错/5xx/异常P0
INFO业务规则观察 / 跨系统 stub观察

五条质量纪律（凭什么可信）

杜绝假绿·每步后端回查坐实再下结论·先读源码点不到就算红诚实暴露 GAP泳道不压平

④ 最终结果是 HTML

每轮测试跑完 → harness/reports/report.html：单文件、自包含、浏览器打开即用。左侧选系统(带 UI驱动%/通过率/问题数)，右上该系统正常流程逐步骤(端·应然·实测·判定·驱动UI-HTTP·截图)，右下当前问题+修复意见。这就是交给评审/团队的东西。

⑤ 怎么把这套方法丢给别人（分发）

这套方法 = 一个 Claude Code 全局技能目录 ~/.claude/skills/flow-probe/。

  1. 打包：
    zip -r flow-probe-skill.zip ~/.claude/skills/flow-probe
  2. 发给对方，对方解压到自己的 ~/.claude/skills/flow-probe/(全局，跨项目生效)，下次 Claude Code 会话即识别。
  3. 只想让人「看懂方法 + 怎么用」：单独发本文件 flow-probe-guide.html，浏览器打开就懂。

⑥ 别人拿到后怎么用（在自己项目落地）

  1. 把 skill 的 assets/ 里 flow-probe-lib.mjs/build-report.mjs/run-stack.sh.tmpl(改名 run-stack.sh)/example-flow-probe.mjs 拷进本项目 harness/；装 Playwright(npm i -D playwright && npx playwright install chromium)。
  2. cp flow-probe.config.example.mjs flow-probe.config.mjs，照 references/adapt-to-new-project.md 填本项目的 urls / 登录端点 / token 键 / 账号 / 系统清单；改 run-stack.sh 顶部 CONFIG(建库/迁移/前后端启动/端口)。
  3. 对 Claude 说「跑探针 <系统>」→ 本 skill 自动加载方法。
  4. 照 example-flow-probe.mjs 为该系统写 <code>-flow-probe.mjs(逐流程·落端·浏览器点真按钮·后端回查)。
  5. bash harness/run-stack.sh <系统> 起隔离栈跑 → 产 harness/reports/report.html。
  6. 看 report.html 问题清单 → 改产品代码 → 重跑 → findings 转绿。

⑦ 两个真实例子（为什么这么测有价值）

例A · 正常流程怎么被测：三级审核(撰写→提交→二审→三审→发布)。探针以经办人上下文点「提交审核」→回查审核中；辖区审核员在审核待办点「通过」→办公室审核员点「通过」→回查通过；点「发布」→回查已发布。全程浏览器点真按钮 + 后端坐实，全 PASS。
例B · 测出真 bug 并闭环(接口测试发现不了)：探针要在审核待办页点「通过」办结时，发现该页面只读、根本没有通过按钮——审核员无法在页面办结。判红记根因 → 改产品代码(前端补操作列 + 后端 review 分派) → 重跑 → 转绿。这条只有"逐步骤点真页面"才会暴露。

⑧ 触发词 & 参考实现

对 Claude 说以下任一，即进入本方法：跑探针 <系统>深探针 <系统>flow-probe <系统>浏览器真流程测试按流程图测业务系统

参考实现：一个多系统业务平台的 harness/——覆盖多个系统并包含细化流程文档，是本方法的完整落地样板。
