# 不变的方法论内核（任何项目通用）

## 四条核心原则
- **A 契约 + 约束先行**：UI 之前先冻 OpenAPI 契约 + DB 约束（FK/unique/not-null/enum）。引用完整性由 DB 外键保证，不只靠 UI。
- **B 共享内核单一真源**：org/user/RBAC/dict/region/业务系统名录 最先建、全局唯一。所有系统引用一律指向内核 FK，禁自建。这一条同时解决：引用实体下拉、非必要不增表、跨系统流程通。
- **C 探针/真跑驱动验收**：脏数据探针（投毒 999999 → 后续段与聚合层强断言真实展示，显示 mock/兜底即脏）；或至少真跑主链路 e2e。
- **D 依赖分层，不平行**：系统按 DAG 排序，地基（认证/组织/字典/区划/业务系统名录）先行，聚合层（地图/监管/门户）最后。

## 五道质量门（每系统 DoD）
1 契约门 OpenAPI camelCase+完整enum+容错 · 2 约束门 FK/ENUM/防孤儿 · 3 探针门 红→绿 · 4 评审门 独立对抗复核 · 5 运行门 真跑主链路。
**DoD = 编译绿 + P0 对抗清零 + 评审过 + 真跑通 + 覆盖矩阵如实（P1入backlog）。**

## ★做实纪律（最重要，反表面功夫）
"编译过 + 接口返 200" **不等于**功能做完。一个功能算"做实"必须全部满足：
1. **端到端串通**：不是孤立 CRUD/死字段；相关实体真串起来（如 权限→菜单→角色→用户→可见菜单 真通）。禁"字段建了不驱动逻辑""模块建了彼此不串"。
2. **真实种子数据**：每模块发 Flyway seed，登进去就有可用可见数据（含几个不同角色的探针用户）。空模块=表面功夫。
3. **探针驱动验收**：灌真实数据→走真用户流程→断言**用户看得见的正确性**；凡"因人/因角色/因状态而不同"的功能必须断言**确实不同**（如不同角色可见菜单不同）。非"200 OK"。
4. **无假绿**：外部依赖诚实 stub/backlog；状态/成功率来自真实记录，禁硬编码 100%/纯 DB 态兜底冒充"已送达/已持久化"。
5. 机械化：把上述做成可运行的 harness（隔离启动+断言种子非空+角色差异+无假数据），当作 DoD 门跑，非人肉自查。
> 完整反模式清单见目标工程 `docs/DEV-DISCIPLINE.md`；harness 范例见 `harness/verify-real.sh`。

## 对抗式验收（关键，为何常需 2-4 轮）
生成 agent 的自报成功**不可信**。每轮结束由**独立复核 agent** 判定 P0 是否真清零、真跑是否通过；复核给否则起定点修复轮（并行修 P0 + 门 + 再独立复核），直到清零。历史上"编译过/自报修好"多次被复核证伪（软删撞键、retry死结、越权、乐观锁名存实亡、命名错配、建错系统）。

## 常见"编译过但跑不通/建错"雷区（提前防）
- 编译过≠跑得通：真库迁移语法（5.7 CHECK被忽略/字符集/FK引UNIQUE/索引长度）、Mapper未扫描、Security拦截、种子密码占位、字段映射。
- 语义错配：grounding 预贴标签→建错系统（务必中立提取）。
- 假数据：硬编码 100% 成功率/假回执/兜底堆积数——一律禁止，缺依赖标 stub/backlog。
- 覆盖假象：编译+P0清零掩盖"只建了需求一小块"——靠覆盖矩阵对照真源照出缺口。

## 流水线（从原始文档到能跑的系统）
Phase0 架构锁定（kando-macro-architecture-extractor：原型/PRD→架构+页面契约+探针；一次性锁系统清单+DAG+共享实体+GoldenPath，ambiguities 熔断）→ Phase1 共享内核 → Phase2 逐系统全栈闭环（见 system-builder）→ Phase3 跨系统集成（探针 5_crossref 穿透 + GoldenPath e2e）。
产品层 spec 用 kando-product-spec-generator（架构产物→PRD/菜单/覆盖矩阵/data-model/contracts）。
